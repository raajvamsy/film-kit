01 · The constraint

One small box. Up to ten people.

Every design choice follows from this. A preview container has a hard 2.5 GB memory cap and serves 5–10 users at once — roughly 200–400 MB each.

2,536 MB cap
0idle ~400 MBcap

What that rules out

  • No dev server kept running per project
  • Builds are short-lived; caches live on disk, not in memory
  • No user's project code is ever shared with another project
02 · Old vs new

Same edit. Very different amount of work.

Press “Make an edit”. The old builder redoes every step. The new one skips what hasn't changed and patches the open preview.

06 · Big apps

Build the pages you use, not all of them.

Large apps can have 600–800 pages, but a developer touches a handful at a time. The working set builds those, and turns the rest into light stubs that build the moment you open them.

07 · You stay in control

Two switches in wm_rn_config.json

The new preview is on by default. Teams can fall back or opt in per project.

Fall back to the classic builder

If a project misbehaves on the new preview.
"profile": "legacy-web-preview",

Build only the pages you need

Opt-in, for big apps.
"preview": {
    "allPages": false,
    "pages": ["Main", "Dashboard"]
},
